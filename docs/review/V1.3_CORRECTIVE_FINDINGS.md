## Purpose

This document records substantive issues identified after the manuscript v1.3 artifact had already been frozen. It does not rewrite or invalidate the historical artifact. Instead, it defines the correction scope and acceptance criteria for the next research release.

The v1.3 artifact remains reproducible under its declared tests and experiments. The findings below show that those tests did not cover several adversarial or semantic-alignment cases. The v1.4 work therefore focuses on mathematical–implementation alignment, fail-closed behavior, and clearer separation among:

1. mathematical specification;
2. executable counterpart;
3. integrated runtime path; and
4. empirical or adversarial validation.

## Finding F1 — Equation 15 information-gain mismatch

### v1.3 manuscript intent

Equation 15 defines an expected reduction in uncertainty over model parameters:

```text
IG(r) = H[p(Theta | D)] - E_F_r[ H[p(Theta | D, r, F_r)] ]
```

### v1.3 implementation

`research_core/active_learning.py::expected_information_gain` computes the reduction in predictive categorical entropy after one posterior-predictive observation. That is a different quantity from parameter-posterior entropy reduction.

For the symmetric Beta/Dirichlet case `alpha=(1,1)`:

- parameter-posterior expected entropy reduction: approximately `0.19314718056`;
- current predictive categorical entropy reduction: approximately `0.05663301227`.

### v1.4 correction

Keep the manuscript concept as parameter-posterior information gain and implement that quantity explicitly. Preserve predictive entropy reduction only under a distinct name and description if it remains useful as a diagnostic.

### Acceptance criteria

- a deterministic regression test reproduces the `alpha=(1,1)` parameter-information-gain value to declared numerical tolerance;
- predictive entropy reduction is not exposed under the same function name or Eq. 15 label;
- manuscript, code, tests, and math-to-code audit use one consistent definition.

## Finding F2 — Vector ECE can hide systematic high-confidence errors

### v1.3 implementation

`research_core/evaluation.py::vector_ece` groups observations by maximum predicted probability, averages prediction vectors and one-hot outcomes within each bin, then computes an L1 difference between those averages.

This aggregate can cancel opposing classification errors. For example, two observations can each be wrong with 0.9 confidence while the bin-level average prediction vector matches the average outcome vector, yielding zero vector ECE.

### v1.4 correction

Do not use this vector ECE as the sole calibration diagnostic. Introduce a calibration measure whose semantics are explicit and whose adversarial behavior is tested, while retaining Brier score and log loss as complementary proper scoring rules.

The preferred v1.4 manuscript-facing choice is top-label ECE unless the implementation and manuscript jointly adopt a stronger classwise alternative.

### Acceptance criteria

- an adversarial fixture with two 0.9-confidence wrong predictions must not report perfect calibration;
- Brier score and log loss remain available;
- the manuscript does not present ECE alone as evidence that calibration has been established;
- any retained vector-ECE helper is labeled as supplementary rather than normative.

## Finding F3 — Compatibility-masked evidence can still increase data support

### v1.3 manuscript intent

The manuscript defines effective evidence mass for support using evidence associated with permitted categories.

### v1.3 implementation

`research_core/service.py::prioritize_followups` obtains `effective_mass` from `weighted_counts(..., request.categories, ...)` before compatibility masking and later computes:

```text
support = data_support(effective_mass, request.support_tau)
```

Therefore authorized evidence assigned exclusively to a category later excluded by the compatibility mask can still increase support and can help the output cross an abstention threshold.

### v1.4 correction

Compute released data support only from effective mass assigned to currently permitted categories. Evidence excluded by compatibility must not increase the support score used to release a practice priority.

### Acceptance criteria

- adding any amount of otherwise-valid evidence solely to masked categories leaves released data support unchanged;
- masked-only evidence cannot move a request from abstention to release;
- the test covers both a below-threshold and above-threshold boundary case;
- the implementation and manuscript use the same definition of effective evidence mass.

## Finding F4 — Zero permitted mass in a routing component becomes a uniform distribution

### v1.3 implementation

`research_core/routing.py::route_mixture` normalizes each routing-level distribution over the permitted category set.

`research_core/inference.py::normalize` returns a uniform distribution when the selected category set has total mass less than or equal to zero.

As a result, a routing level with no probability mass on any permitted category can be converted into an artificial uniform component instead of being treated as unsupported.

### v1.4 correction

Routing normalization must distinguish:

- a valid positive-mass distribution requiring normalization; from
- an unsupported zero-mass component.

Zero-permitted-mass components must be excluded from the routing mixture. If no eligible positive-mass component remains, the runtime must fail closed through backoff or abstention.

### Acceptance criteria

- zero permitted mass never produces a uniform routing component;
- unsupported components do not contribute routing weight;
- if every authorized/applicable component has zero permitted mass, the output abstains with an explicit reason;
- positive-mass routing behavior remains deterministic and normalized.

## Finding F5 — Hierarchical model semantics exceed the implemented uncertainty propagation

### v1.3 manuscript framing

The hierarchy is written using generic → archetype → industry → company Dirichlet structure.

### v1.3 implementation

`research_core/inference.py::hierarchical_partial_pooling` recursively passes the posterior mean of one level as the fixed prior distribution for the next level. The implementation is therefore a recursive plug-in hierarchical Dirichlet shrinkage approximation.

`credible_intervals` samples from a supplied Dirichlet posterior conditional on its alpha vector. It does not propagate uncertainty from the parent hierarchy through all levels.

### v1.4 correction

Use precise terminology:

- `recursive plug-in hierarchical Dirichlet shrinkage` for the dependency-free reference implementation;
- `conditional Dirichlet intervals given the plug-in parent distribution` for the current interval calculation.

Add a separate synthetic benchmark that compares the plug-in approximation with an uncertainty-propagating reference across sparse and denser regimes.

### Acceptance criteria

- no manuscript text claims that the lightweight reference implementation propagates full parent-level posterior uncertainty;
- uncertainty intervals are explicitly labeled conditional;
- the benchmark reports at least sparse, medium, and denser evidence regimes;
- the benchmark is presented as an approximation analysis, not as proof of external validity.

## Finding F6 — Equation coverage and runtime integration were not sufficiently distinguished

### v1.3 audit language

The v1.3 audit records executable counterparts for all 15 mathematical expressions and reference counterparts for the listed public algorithms.

### v1.3 limitation

Several utilities are not part of the single `prioritize_followups` runtime path. Examples include:

- DAG factorization;
- logistic stopping;
- calibration metrics;
- KL drift;
- information-gain utilities.

Therefore “has an executable counterpart” must not be conflated with “is integrated into one end-to-end service path” or “has been empirically validated.”

### v1.4 correction

Add an implementation/integration coverage matrix that assigns each equation or algorithm to one of the following states:

1. executable standalone utility;
2. integrated candidate-side runtime path;
3. evaluation/monitoring utility;
4. experimental-only utility;
5. empirically validated — only where external evidence actually supports that status.

### Acceptance criteria

- all manuscript equations are mapped to both an implementation status and an integration status;
- “15/15 implemented” is never used as shorthand for “full pipeline validated”;
- the manuscript distinguishes structural verification, controlled synthetic verification, and external empirical validation.

## v1.4 adversarial verification plan

### Experiment 4 — Adversarial Mathematical Alignment

At minimum, Experiment 4 must contain deterministic fixtures for:

1. Eq. 15 parameter-information-gain counterexample;
2. high-confidence wrong-prediction calibration cancellation;
3. masked-only evidence support inflation;
4. zero-permitted-mass routing behavior.

Each fixture must include:

- the v1.3 behavior;
- the v1.4 expected behavior;
- a precise pass/fail assertion;
- a declared numerical tolerance where applicable.

### Experiment 5 — Hierarchy Approximation Benchmark

Experiment 5 should compare recursive plug-in hierarchical shrinkage against an uncertainty-propagating reference under synthetic evidence regimes.

At minimum:

- sparse regime;
- intermediate regime;
- denser regime;
- comparison of posterior means;
- comparison of uncertainty interval width or coverage behavior;
- explicit statement that the benchmark concerns internal approximation behavior, not employer validity or employment outcomes.
